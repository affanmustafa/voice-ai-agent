# Architecture & Design Decisions

Running log of decisions made during development. This will feed into the final README.

---

## Audio Format — PCM

**Decision:** Use raw PCM (16-bit, 16kHz, mono) for audio frames between the fake client and our FastAPI server.

**Why:** No Twilio in our stack, so there's no reason to use μ-law (pcmu), which exists primarily for telephony compatibility. PCM is simpler to generate from a wav file, requires no encoding/decoding step, and is what OpenAI Realtime API accepts natively.

---

## Fake Client Audio — Real Speech Recording

**Decision:** Stream a real speech wav file from the fake client rather than generated silence.

**Why:** Since we're using the real OpenAI Realtime API, it will actually transcribe whatever audio we send. A real speech file produces a real transcript, making the barge-in demo meaningful and convincing.

---

## LLM / Voice Pipeline — OpenAI Realtime API

**Decision:** Use the OpenAI Realtime API as a single-provider shortcut rather than a chained mock pipeline (Deepgram → LLM → ElevenLabs).

**Why:** The PDF explicitly offers this as a valid path. It handles STT, LLM, and TTS in one WebSocket connection, reducing complexity significantly. The interfaces and timing logic — not the integrations — are what's being graded. Trade-off: less visibility into individual pipeline stages, but latency instrumentation can still be done at the bridge layer.

---

## Transcript Storage — Shared `/data/calls/` Folder

**Decision:** Transcript JSON files are written to a shared `/data/calls/` directory at the project root, outside both services.

**Why:** The Python service writes transcripts and the Next.js service reads them. A shared folder at the root avoids either service reaching into the other's directory, keeping boundaries clean. In a production system this would be a database — this is the simplest equivalent for a local demo.

---

## Call ID — Generated by the Fake Client

**Decision:** The fake client generates a UUID before connecting and passes it in the WebSocket URL as `/ws/{call_id}`.

**Why:** The client initiates the call, so it owns the call ID. This mirrors how real telephony works — the caller's session ID is assigned at the edge, not by the backend. It also makes it easy to correlate the streamed audio file with the resulting transcript.
